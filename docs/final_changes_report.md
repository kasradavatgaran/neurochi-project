# گزارش تغییرات نهایی — ۱۳ اکتبر ۲۰۲۶

## نتیجهٔ اجرا

لندینگ، تکمیل ثبت‌نام با اولین فرزند، انتقال پایدار سؤال مهمان به چت عمومی، تاریخچهٔ تست و کارت بازی، هدایت به تست، تغییر مدل و اصلاحات سرعت/RAG در کد محلی پیاده شدند. نسخه روی سرور اصلی سایت دیپلوی نشده است.

لندینگ همان HTML و تصاویر ارسالی را استفاده می‌کند. پنج تصویر بزرگ با تبدیل lossless از ۱۱٬۸۷۰٬۷۳۲ به ۸٬۲۰۱٬۰۴۴ بایت رسیدند؛ برابری پیکسل‌های RGBA پس از تبدیل بررسی شد. فایل HTML اولیه حفظ شده است. صفحات فرم، تست و نمودار به‌صورت lazy بارگذاری می‌شوند؛ JS اولیه از حدود ۱٫۱۲ MiB به حدود ۲۰۲ KiB کاهش یافت. تصاویر و پس‌زمینهٔ قدیمی هنوز هشدار اندازهٔ asset دارند.

سؤال مهمان پیش از ورود در مرورگر با شناسهٔ یکتا نگهداری می‌شود. بعد از ثبت والد و اولین فرزند، backend یک job و session عمومی مستقل ایجاد می‌کند. پاسخ پس از ورود تولید و در همان session ذخیره می‌شود. رفرش صفحه، تکرار درخواست و restart backend باعث ساخت session/پاسخ تکراری نمی‌شوند. خطای سرویس، سؤال را در حالت قابل‌تلاش‌دوباره حفظ می‌کند. حذف session مالکیت را بررسی و پیام‌ها، منابع و job تکمیل‌شدهٔ آن را پاک می‌کند؛ حذف job در حال اجرا تا پایان پاسخ مجاز نیست.

تاریخچهٔ تست، تاریخ، حوزه، نتیجه، جواب‌های قبلی و بازی‌های انجام‌شده را نمایش می‌دهد. بازی‌های جدید به session تست مرتبط می‌شوند؛ برای رکوردهای قدیمی که این رابطه ذخیره نشده بود، ارتباط بر اساس حوزه و زمان استنتاج می‌شود و در API با `link_inferred` مشخص است.

## علت‌های مشخص‌شده و اصلاحات

- درخواست‌های همگام Liara در endpoint `async` باعث معطل‌شدن سایر درخواست‌ها می‌شدند. چت در thread pool اجرا می‌شود و فراخوانی‌های صوت نیز از event loop خارج شدند.
- embedding سؤال و chunkهای کاندید قبلاً در دو رفت‌وبرگشت جدا اجرا می‌شد. اکنون موارد cacheنشده در یک batch ارسال و نتیجه به‌صورت پایدار ذخیره می‌شود؛ cache پس از restart باقی می‌ماند.
- بازسازی حافظهٔ کودک در هر چت، کوئری‌های تکراری و نگه‌داشتن transaction نوشتن تا پایان مدل حذف شدند. تمام نتایج تست/بازی حفظ می‌شوند؛ جزئیات جواب‌ها بر اساس ارتباط با سؤال به prompt اضافه می‌شود.
- هنگام خواندن هر پیام قدیمی، کل corpus دوباره برای metadata منابع پیمایش می‌شد. اکنون lookup از index ازپیش‌ساخته استفاده می‌کند.
- فهرست sessionها برای شمارش پیام‌ها N+1 query داشت؛ شمارش اکنون یک query گروهی است. فهرست تاریخچهٔ تست صفحه‌بندی دارد و جزئیات را فقط هنگام درخواست نتیجه می‌خواند.
- SQLite از WAL، ایندکس‌های موردنیاز، busy timeout و transactionهای کوتاه استفاده می‌کند. `synchronous=FULL` حفظ شده است. مسیر فایل DB مستقل از working directory شده تا فایل اشتباه/خالی انتخاب نشود.
- frontend پاسخ رسیده را با سقف ۵ کاراکتر در ۳۰ میلی‌ثانیه نمایش می‌داد؛ این تأخیر مصنوعی برطرف شد.
- query bridge برای سؤال واضحِ فارسی، متن همان سؤال را استفاده می‌کند؛ سؤال نیازمند بازنویسی با Flash Lite به یک سؤال فارسی تبدیل می‌شود. سن صریح پرسش حفظ می‌شود و سن کودک فقط در صورت نبود سن در پرسش اضافه می‌شود. شمارش ماه‌های کامل تقویمی، خطای «۳۵ ماه به‌صورت ۳۴ ماه» را رفع کرد.

## اندازه‌گیری پاسخ

این نمونه‌ها روی همین سیستم، با سؤال آزمایشی «کودک ۱۰ ماهه به چند ساعت خواب نیاز دارد؟» و مدل 3.8 Flash ثبت شدند. «قبل» مربوط به قبل از اصلاحات RAG است، نه مقایسهٔ 3.5 با 3.8. نتایج، تضمین تأخیر ثابت سرویس نیستند.

| وضعیت | اولین متن قابل‌نمایش | پایان پاسخ | حجم prompt پاسخ |
|---|---:|---:|---:|
| قبل، cache سرد | ۲۲٫۶ ثانیه | ۲۷٫۰ ثانیه | ۲۱٬۱۱۸ کاراکتر |
| قبل، cache گرم | ۶٫۹ ثانیه | ۱۱٫۴ ثانیه | ۲۱٬۱۱۸ کاراکتر |
| بعد، cache سرد | ۱۴٫۲ ثانیه | ۱۸٫۵ ثانیه | ۱۰٬۶۲۶ کاراکتر |
| بعد، cache گرم | ۳٫۶ ثانیه | ۹٫۶ ثانیه | ۱۰٬۶۲۶ کاراکتر |
| بعد از restart، cache حفظ‌شده | ۴٫۲ ثانیه | ۹٫۱ ثانیه | ۱۰٬۶۲۶ کاراکتر |

زمان SQL این درخواست‌ها حدود ۰٫۵ تا ۱٫۳ میلی‌ثانیه بود. درخواست‌های health در زمان تولید پاسخ معمولاً ۲ تا ۵ میلی‌ثانیه پاسخ گرفتند؛ چند نمونه تا حدود ۲۳ میلی‌ثانیه رسیدند.

کنترل جداگانه، فقط با یک prompt ۲۴ کاراکتری و بدون RAG/DB، حدود ۵٫۳ ثانیه تا اولین متن زمان برد. این زمان مربوط به مسیر فعلی Liara و مدل است؛ اندازه‌گیری، زمان Google را از gateway و شبکهٔ Liara جدا نمی‌کند. در موضوع کاملاً جدید، embeddingهای cacheنشده هنوز ممکن است چند ثانیه تأخیر اضافه کنند.

## RAG و منابع

corpus اولیه شامل ۳٬۸۰۷ مقاله و ۱۰٬۱۹۳ chunk بود. بررسی نهایی ۳۱ فایل خالی یا صرفاً دارای لینک را مشخص کرد؛ دو فایل خالی قبلاً chunk نداشتند و ۲۹ ورودی بدون متن واقعی از index کنار گذاشته شدند. فایل‌های اصلی حفظ شدند. index نهایی شامل ۳٬۷۷۸ مقاله و ۱۰٬۱۶۴ chunk است: ۲٬۶۳۶ BabyCenter، ۹۱۱ Kinedu و ۹۰ NHS، به‌علاوهٔ منابع قدیمی دیگر. نبود Kinedu/NHS در index علت مشکل نبود. تعداد زیاد BabyCenter، tokenization نامناسب، فایل‌های بدون محتوا و انتخاب کاندیدها بر اساس متن، بر نتایج اثر داشتند.

جست‌وجوی صرفاً عنوان در خواب بهتر بود، ولی در تغذیه/پریدن بعضی نتایج ضعیف‌تری داشت. اکنون کاندیدهای عنوان و متن ترکیب و سپس semantic ranking اجرا می‌شوند. semantic حذف نشده است. تا ۱۰ کاندید به semantic می‌رسد، تا ۵ مقالهٔ متمایز رتبه‌بندی می‌شود و حداکثر ۲ chunk به prompt پاسخ می‌رود.

قبل، هر سند بازیابی‌شده—even اگر مدل استفاده نمی‌کرد—به citation تبدیل می‌شد. اکنون مدل شناسهٔ اسناد واقعاً استفاده‌شده را اعلام می‌کند؛ marker داخلی در stream نمایش داده نمی‌شود. فقط اسناد اعلام‌شده، با عنوان کامل و URL اصلی، نمایش داده می‌شوند. این قرارداد احتمال ارجاع نامرتبط را کاهش می‌دهد و به معنی تضمین کامل grounding مدل نیست.

تست واقعی خواب، منبع مرتبط Kinedu و BabyCenter برگرداند. سؤال استریل‌کردن شیشه‌شیر، Kinedu و NHS را با URL صحیح برگرداند. سؤال خواب دیگر با مقدمهٔ نامرتبط دربارهٔ کره پاسخ نگرفت. تست‌های تغذیه نیز منبع موضوعی Kinedu برگرداندند.

در بررسی ساختاری ترجمه‌های Kinedu/NHS، مورد فاقد متن فارسی یا کوتاه‌تر از حد تعیین‌شده یافت نشد؛ نمونه‌های خواب و استریل‌کردن هم بررسی شدند. بازترجمهٔ جمعی انجام نشد. این بررسی جایگزین بازبینی کامل علمی/زبانی تمام مقاله‌ها نیست.

## بازی‌ها و بازه‌های سنی

واردکننده، `gameCategoryId` را به‌جای `testCategoryId` به حوزهٔ ASQ نگاشت کرده بود. طبقه‌بندی ۶۹۳ رکورد موجود با حفظ IDها و پاسخ‌های قبلی اصلاح شد. در ۳۵ ماهگی، هر پنج حوزه ۶ بازی در فایل اصلی دارد.

پوشش بازی‌های حوزه‌دار از روز ۱ تا روز ۱۹۸۰ پیوسته است. برای روز تولد و سن بالاتر از ۱۹۸۰ روز، بازی حوزه‌دار در دادهٔ فعلی وجود ندارد؛ محتوا یا بازهٔ سنی جدید اختراع نشده است. رکوردهای بدون حوزهٔ معتبر، «عمومی» نگه داشته شدند. دو رکورد قدیمیِ متن‌یکسان، با حفظ ID و بدون جعل شناسهٔ منبع، عمومی شدند.

## اعتبارسنجی و وضعیت محلی

- ۱۸ تست backend موفق: مالکیت، تاریخچه و جواب‌ها، صوت عمومی، هدایت تست، هم‌زمانی، آزادشدن lock، حذف session، retry و resume سؤال لندینگ، cache پایدار، citation، سن/query و حذف ورودی‌های فاقد متن از index. عبارت محاوره‌ای «خوب نمیتونه بپره» هم برای تطبیق با مقالهٔ پریدن تست شد؛ متن query به فهرست مترادف‌ها تبدیل نمی‌شود.
- `npm run lint -- --no-fix` بدون خطا؛ `npm run build` موفق. هشدارهای اندازهٔ asset و قدیمی‌بودن دادهٔ Browserslist باقی است.
- مهاجرت روی کپی DB قبلی تست شد؛ IDهای والد، کودک، session، پیام، تست، جواب و بازی حفظ شدند. query تاریخچه از ایندکس استفاده می‌کند و full scan قبلی حذف شده است.
- مسیر لندینگ → OTP آزمایشی بدون SMS → فرم والد → اولین فرزند → پاسخ در چت عمومی، در مرورگر بررسی شد؛ رفرش وسط تولید پاسخ نیز تست شد.
- پنجرهٔ نتیجه و کارت بازی، هدایت از چت به تست درست، layout موبایل/دسکتاپ و نبود overflow افقی در لندینگ/تاریخچه بررسی شدند. آزمون روی دستگاه فیزیکی Safari iOS/Chrome Android انجام نشده است.

پشتیبان اولیهٔ DB: `backend/backups/pre-final-changes-20261013.db`.

Backend محلی: `http://127.0.0.1:8000`؛ frontend محلی: `http://127.0.0.1:18080`.

در محیط استقرار، تنظیمات `.env` نیز باید اعمال شوند چون این فایل در git نیست:

```dotenv
LIARA_CHAT_MODEL=google/gemini-3.8-flash
LIARA_QUERY_MODEL=google/gemini-3.5-flash-lite
RAG_MAX_SOURCES=2
RAG_QUERY_REWRITE_MODE=auto
```

کلید و base URL موجود Liara حفظ شده‌اند. تست‌ها روی DB جدا انجام شدند؛ حساب آزمایشی به DB اصلی اضافه نشده است.
